# Buildkite Agent Infrastructure

This skill encodes how to choose, deploy, and operate a self-hosted Buildkite agent fleet — Elastic CI Stack (AWS/GCP), Agent Stack for Kubernetes (`agent-stack-k8s`), hand-rolled VMs, or Buildkite hosted agents. It covers the decision rules, queue design, controller tuning, lifecycle hooks, tokens, and failure modes the docs catalogue but do not opinionate on.

This skill covers everything *outside* a running job step. For `buildkite-agent` subcommands invoked *inside* a job — annotate, artifact, meta-data, OIDC, lock, env, secret, redactor — see the **buildkite-agent-runtime** skill.

## Quick Start — compute platform decision tree

| Workload | Recommended platform |
|---|---|
| Linux, AWS, <500 agents/build, no K8s mandate | Elastic CI Stack for AWS |
| Linux, mixed cloud or existing K8s investment with K8s operators on call | Agent Stack for Kubernetes |
| Linux, GCP, <200 agents/build | Elastic CI Stack for GCP |
| macOS / iOS builds | Buildkite hosted agents (macOS) or self-managed EC2 Mac |
| Windows | Self-managed Windows VM (no first-class stack) |
| Spiky parallelism, ≤5,000 concurrent jobs, no infra team | Buildkite hosted agents |
| Strict network egress / VPC-only / regulated workloads | Self-hosted, not hosted |
| First-time customer, no infra team | Buildkite hosted agents |

**Never choose `agent-stack-k8s` because the org has a Kubernetes cluster. Choose it because the org has Kubernetes *operators*.** The controller's failure modes assume K8s fluency (`podSpecPatch`, strategic merge patches, scheduler events, init-container exit codes). Without that fluency, use Elastic CI Stack.

### Minimum-viable install — Agent Stack for Kubernetes

```bash
# Create the cluster token secret (rotate annually; never bake into chart values)
kubectl create namespace buildkite
kubectl -n buildkite create secret generic buildkite-agent-token \
  --from-literal=BUILDKITE_AGENT_TOKEN="$BUILDKITE_AGENT_TOKEN"

# Install the controller; always pin --version
helm upgrade --install agent-stack-k8s \
  oci://ghcr.io/buildkite/helm/agent-stack-k8s \
  --namespace buildkite \
  --version 0.29.5 \
  --set agentStackSecret=buildkite-agent-token \
  --set 'config.tags={queue=kubernetes}'
```

For Elastic CI Stack for AWS, the equivalent minimum-viable install is the CloudFormation template at `https://s3.amazonaws.com/buildkite-aws-stack/latest/aws-stack.yml` — deploy with `aws cloudformation deploy --template-url ... --parameter-overrides BuildkiteAgentToken=<token>`.

> For pushing custom hosted-agent images, namespace.so integration, and concurrency caps, see the **buildkite-hosted-agents-operations** skill.

## Phase 1 — Choose a compute platform

Each row's "known failure modes" cite escalations encoded in the Phase 3 gotcha table or Phase 5 disconnect table.

| Platform | Strengths | Weak spots | Known failure modes | Cost model |
|---|---|---|---|---|
| Elastic CI Stack for AWS | Mature, opinionated, autoscaling via `agent-scaler` + `lifecycled` | AWS-only; AMI build pipeline owned by user; lifecycled EOL on Amazon Linux 2 | Sudden disconnects under network drop (Phase 5 disconnect triage) | EC2 + EBS + spot/on-demand |
| Elastic CI Stack for GCP | Native GCP equivalent | Smaller user base, fewer reference deployments | Less battle-tested than AWS variant | GCE + persistent disk |
| Agent Stack for Kubernetes (`agent-stack-k8s`) | Cloud-portable, leverages existing K8s infra, declarative | Every chart upgrade is a breaking change; controller is single point of failure unless replicated; opaque scheduling failures | Phase 3 rows: localHookPath regression, hugepages lowercase, missing K8s events on stalled jobs, build-dir change on chart bump, image-pull-policy not applied to checkout/agent containers | K8s node cost + controller pod |
| Hand-rolled VMs | Fully controlled, fits unusual platforms (Windows, FreeBSD, bare-metal) | Operator builds everything — autoscaling, image lifecycle, hook plumbing | No upstream support contract for scaling logic | Bespoke |
| Buildkite hosted agents | Zero infra to operate; fast onboarding | Limited customization; egress and IP constraints; hosted-image lifecycle limited | Image push gap blocks bootstrap workflows; namespace.so admin surface separate from Buildkite UI | Per-minute by instance shape |

Hard rule for the AWS variant: do not run a single `agent-scaler` Lambda for a production cluster — its failure is a silent SPOF that surfaces as queue backlog without explanation. Pair with CloudWatch alarms on scaler invocation failure.

## Phase 2 — Queue design

A queue is a routing primitive that pairs a tag (`queue=<key>`) with an agent population. Three valid patterns:

1. **Per-workload queue (default).** Examples: `linux-amd64-large`, `linux-arm64-small`, `macos-m4-large`. Splits along OS, architecture, and instance shape. Use this until cost attribution forces another axis.
2. **Per-team queue.** Only when teams own infrastructure budgets and need cost attribution. Adds operational toil — every queue is a new scaling target.
3. **Per-cost-center queue.** For chargeback to internal customers. Requires queue-to-budget mapping maintained outside Buildkite. Justify before adopting.

**Do not create a queue per pipeline.** Queues are a routing primitive, not a namespace. A queue per pipeline produces a routing explosion (no agent shares idle capacity) and makes scaling intractable.

### Sizing heuristic

| Builds/day | Concurrent agents (steady-state) | Queue strategy |
|---|---|---|
| <1,000 | 5–20 | Single queue is fine |
| 1,000–10,000 | 50–500 | Split per-OS, per-size |
| 10,000–100,000 | 500–5,000 | Per-workload queues mandatory; observability prerequisite |
| >100,000 | 5,000+ | Multi-cluster, per-workload, scaler tuning required |

Apply Little's Law to size queues against a target P95 wait time. See `agent-infrastructure/references/queue-design-patterns.md` for worked examples at 1k, 10k, and 100k builds/day.

### Hard gate before scaling beyond 10,000 builds/day

Queue depth alerting must be in place before adding queues to absorb spikes. Without `P95(wait_time_per_queue)` instrumented, adding capacity is guesswork. See Phase 6.

## Phase 3 — Agent Stack for Kubernetes controller setup

The Agent Stack for Kubernetes controller polls the Buildkite Agent API for jobs tagged `queue=<key>`, generates a Kubernetes `PodSpec`, and creates a `Job` per Buildkite job. The PodSpec composes (in order): user-supplied `podSpec` from the `kubernetes` plugin, `extra-volume-mounts`, the `agent` container, the `checkout` container (unless `skip.checkout: true`), `imagecheck-*` init containers, then `pod-spec-patch` from controller config, then `podSpecPatch` from the plugin.

`podSpecPatch` is a Kubernetes strategic merge patch applied *last* — it is the correct lever for overrides that the default generator misses (checkout-container image-pull-policy, hugepages on the agent container, custom volumes).

### The agent-stack-k8s gotcha table

Five real escalations, each with agent/controller version, symptom (verbatim where possible), root cause, and fix. Pin both the agent version and the chart version per queue.

| Symptom | Agent / chart range | Root cause | Fix |
|---|---|---|---|
| **Repository pre-command hooks silently skipped in Kubernetes command containers** | agent ≥3.106.0; controller ≥0.32.0 | `localHookPath` resolution regression in the agent — the command container no longer locates hooks under `.buildkite/hooks` after the agent's hook-discovery logic was refactored | Pin agent ≤3.105.x on the affected queue, OR upgrade to the controller version with the fix; set `localHookPath` explicitly via `podSpecPatch` on the command container to override the default discovery path |
| **Pod spec rejected by the K8s API: `hugepages-2mi` not recognized** | controller using viper config loader prior to fix | Controller's viper config loader lowercases all keys, so `hugepages-2Mi` (case-sensitive Kubernetes resource name) is serialized as `hugepages-2mi` and rejected | Bypass the viper key transform — set hugepage resources via `podSpecPatch` in the `kubernetes` plugin, where keys pass through unmodified to the Kubernetes API |
| **Stalled jobs surface no useful failure message** | all current versions | Controller emits a generic stalled-job report when a pod fails to schedule or terminates abnormally; relevant Kubernetes `Events` (e.g., `FailedScheduling`, `ImagePullBackOff`, `OOMKilled`) are not included in the message surfaced to the build UI | Cross-reference Buildkite job ID with `kubectl -n buildkite get events --sort-by='.lastTimestamp'` filtered by the corresponding Job/Pod name; run `scripts/agent-stack-k8s-diagnose.sh <build-id>` to gather controller logs + events + recent stalled Jobs in one report |
| **Build directory path changed silently after chart upgrade** | chart v0.30.x (workspace volume layout change) | Default workspace volume mount layout changed in the chart; existing pipeline scripts hardcoded the old `$BUILDKITE_BUILD_PATH` and broke | Pin the chart version (`helm upgrade --version 0.29.x`); set `workspaceVolume` explicitly so the path is owned by config, not by the chart default; diff the rendered manifest with `helm template ... \| diff` before any upgrade |
| **`image-pull-policy: Always` not applied to checkout or agent containers** | all current versions when set via controller `image-pull-policy` only | Controller-level `image-pull-policy` applies only to user-defined command containers; `agent`, `checkout`, and `imagecheck-*` init containers retain their generator-default policy | Use `podSpecPatch` to set `imagePullPolicy: Always` on every container by name (`agent`, `checkout`, and each `imagecheck-N`) — controller-level config alone is insufficient |

Closing rule: **every Agent Stack for Kubernetes upgrade is a breaking change until proven otherwise.** Pin the chart, snapshot `helm template ... > rendered.yaml`, diff before applying. See `agent-infrastructure/references/agent-stack-k8s-troubleshooting.md` for the expanded gotcha set, controller log spelunking patterns, and `podSpec` vs `podSpecPatch` worked examples.

## Phase 4 — Lifecycle hooks (operator-side)

The agent runs two categories of hooks:

- **Agent lifecycle hooks** — `pre-bootstrap`, `agent-startup`, `agent-shutdown`. Executed by the agent process at startup/shutdown. Self-hosted only. Live in the agent hooks directory (`hooks-path` config setting; default platform-specific).
- **Job lifecycle hooks** — `environment`, `pre-checkout`, `checkout`, `post-checkout`, `pre-command`, `command`, `post-command`, `pre-artifact`, `post-artifact`, `pre-exit`. Sourced per job, in a per-job shell.

This skill owns where hooks live, when they fire, and how their execution differs by platform.

### Hook execution order (job lifecycle)

| Hook | Locations |
|---|---|
| `pre-bootstrap` | Agent |
| `environment` | Agent, Plugin (non-vendored) |
| `pre-checkout` | Agent, Plugin (non-vendored) |
| `checkout` | Plugin (non-vendored), Agent |
| `post-checkout` | Agent, Repository, Plugin (non-vendored) |
| `environment` (vendored plugin) | Plugin (vendored) — runs *after* checkout |
| `pre-command` | Agent, Repository, Plugin (non-vendored), Plugin (vendored) |
| `command` | Plugin (non-vendored), Plugin (vendored), Repository, Agent |
| `post-command` | Agent, Repository, Plugin (non-vendored), Plugin (vendored) |
| `pre-artifact` | Agent, Repository, Plugin (non-vendored), Plugin (vendored) |
| `post-artifact` | Agent, Repository, Plugin (non-vendored), Plugin (vendored) |
| `pre-exit` | Agent, Repository, Plugin (non-vendored), Plugin (vendored) |

### Hook execution differs between Elastic CI Stack and Agent Stack for Kubernetes

On Elastic CI Stack agents, all hooks run in a single agent process. Exported environment variables flow between phases.

On Agent Stack for Kubernetes, checkout and command phases execute in *separate containers*. Environment variables exported during `pre-checkout`, `checkout`, or `post-checkout` are **not** available to `pre-command`, `command`, or `post-command`. The `environment` hook runs once per container (checkout + each command container), not once per job.

Migration strategies (pass values via shared workspace files or pipeline-level `env:`) are detailed in `agent-infrastructure/references/ec2-to-k8s-migration.md`.

> For commands invoked inside hooks — `buildkite-agent annotate`, `meta-data set`, `secret get` — see the **buildkite-agent-runtime** skill. This skill covers *where hooks live, when they fire, and how they differ between platforms*; the runtime skill covers what commands run inside them.

## Phase 5 — Tokens, agent connection, and disconnect debugging

### Token rotation rules

1. **Use cluster agent tokens, never legacy unclustered tokens.** Cluster tokens scope to a single cluster and are revocable from the cluster's **Agent Tokens** page. Agent Stack for Kubernetes 0.29.0 and later requires a clustered token.
2. **Rotate on a fixed cadence — at most 90 days, not on incident.** Use the `expires_at` field on token creation to enforce the cadence (`POST /v2/organizations/{slug}/clusters/{cluster_id}/tokens` with `"expires_at": "<ISO-8601>"`).
3. **Never embed tokens in AMIs, container images, or chart values.** Inject at agent boot from the platform secret store (AWS Secrets Manager, Google Secret Manager, Kubernetes Secret reconciled by External Secrets Operator). Pass via `BUILDKITE_AGENT_TOKEN` environment variable or `--set agentStackSecret=<k8s-secret-name>` for the Helm chart.
4. **Scope token IP ranges where the agent fleet's egress is stable.** Set `allowed_ip_addresses` (CIDR) on the cluster token.

### Disconnect symptom triage

| Symptom | First check | Second check |
|---|---|---|
| Agents disconnect randomly, no clear error in agent logs | Network MTU and NAT keepalive on the agent host (long-lived TCP connections to `agent.buildkite.com`) | Correlate the agent ID in Datadog `buildkite.agent.heartbeat` (or equivalent) against VPC flow logs around the disconnect window |
| `401 invalid job uuid in job token` mid-job | Agent host clock skew >5 minutes (NTP failure) | Token rotated server-side during the job (check cluster's Agent Tokens audit log) |
| Agents register then immediately drop | Cluster token revoked, expired, or scoped to wrong cluster | Recent cluster token rotation event; verify token's cluster ID matches `BUILDKITE_AGENT_TAGS` cluster tag |
| Wave of disconnects after a Buildkite-side change | Check Buildkite status page for agent-API incidents | Compare against agent-version distribution — a known-bad version may correlate |

Wire `agent.disconnected` events into the on-call pager. The Boston Dynamics Sev 7 outage referenced in `agent-infrastructure/references/agent-stack-k8s-troubleshooting.md` was diagnosed weeks late because nobody was paged on the disconnect signal.

## Phase 6 — Observability of the agent layer

| Need | Tool | Where it surfaces |
|---|---|---|
| Pod-level scheduling latency, queue-depth-vs-pod-create lag | Prometheus scraping the controller's `/metrics` endpoint | See `pages/agent/self_hosted/agent_stack_k8s/prometheus_metrics.md` for the metric inventory |
| Agent connection lifecycle traces (register, dispatch, disconnect) | Datadog or OpenTelemetry agent | `pages/agent/self_hosted/monitoring_and_observability/tracing.md` |
| Queue depth and wait-time per queue | Cluster Queue Job Explorer (Buildkite UI) and Buildkite Insights queue metrics | `pages/pipelines/insights/queue_metrics.md` |
| Controller logs | `kubectl logs -n buildkite deploy/agent-stack-k8s` | First artifact to capture during any incident; enable `config.debug: true` temporarily to increase verbosity |

**If the team cannot answer "what is the P95 wait time for queue X" in under 60 seconds, the cluster is unobservable. Fix that before tuning anything else.** Tuning without observability is gambling.

For incident response, pausing dispatch on a single queue while leaving others active is the right cut: select the queue in the Buildkite UI and choose **Pause Queue** (or call `POST /v2/organizations/{slug}/clusters/{cluster_id}/queues/{queue_id}/pause_dispatch` via the REST API). Jobs already dispatched continue; new jobs wait.

## Phase 7 — Migration: Elastic CI Stack for AWS to Agent Stack for Kubernetes

Phased migration. Effort distribution observed on completed migrations: queue redesign ~30%, pod template tuning ~30%, hook parity ~25%, observability re-plumbing ~15%.

1. **Phase 7.1 — Inventory.** Catalogue every queue, every custom AMI, and every hook file across the EC2 fleet. Record agent version per queue.
2. **Phase 7.2 — Run Agent Stack for Kubernetes in parallel.** Mirror exactly one queue first. Route at most 5% of jobs to the new queue.
3. **Phase 7.3 — Hook parity.** Translate each agent-host hook to its container-context equivalent. Environment variables no longer flow between checkout and command containers (see Phase 4). Most migrations stall here.
4. **Phase 7.4 — Docker daemon parity.** Decide DinD vs Buildkit vs Kaniko vs Depot vs namespace.so per workload. See `agent-infrastructure/references/ec2-to-k8s-migration.md` for the decision tree.
5. **Phase 7.5 — Cutover queue by queue.** Never cut over the whole cluster at once.
6. **Phase 7.6 — Decommission Elastic CI Stack.** After 30 days of green builds on Kubernetes for a given queue, tear down the corresponding EC2 stack.

**Hard gate: complete Phase 7.3 (hook parity) across all workloads on a queue before raising traffic above 5%.** Skipping hook parity is the #1 cause of customer rollback from Agent Stack for Kubernetes to Elastic CI Stack.

## Common Mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Choosing Agent Stack for Kubernetes without K8s operators on call | Stalled-job mysteries with no one to triage | Stay on Elastic CI Stack until on-call K8s expertise exists |
| Per-pipeline queues | Routing explosion, scaling intractable, idle capacity wasted | Queues are per-workload (OS + size), never per-team or per-pipeline |
| Cluster token baked into AMI or container image | Compromise of one host equals full-fleet compromise | Inject at agent boot from the platform secret store |
| No queue-depth or P95 wait-time alerting | Builds queue invisibly until users complain in Slack | Alert on `P95(wait_time)` per queue against an SLA |
| Upgrading the Agent Stack for Kubernetes chart without pinning | Build-dir, workspace path, or image-pull-policy silently change | Pin the chart, diff the rendered manifest before apply |
| Single-replica controller deployment | Controller crash halts all scheduling (silent SPOF) | Run two or more controller replicas with leader election; document RPO/RTO |
| Mixing agent versions across one queue | Version-specific regressions (the agent 3.106.0 hook regression) hit only a fraction of jobs, hard to diagnose | Pin agent version per queue; canary new versions on a single queue first |
| Ignoring `agent.disconnected` events in observability tooling | Sev-class outages root-caused weeks late | Page on disconnect events; correlate with VPC flow logs by agent ID |
| Treating hosted agents as a drop-in for self-hosted | VPC-only or strict-egress workloads break; image lifecycle constraints surface late | Run the hosted-vs-self-hosted audit checklist in `agent-infrastructure/references/queue-design-patterns.md` before committing |
| Controller-level `image-pull-policy` assumed to cover all containers | Checkout and agent containers continue using cached images | Set `imagePullPolicy` via `podSpecPatch` on every container by name |
