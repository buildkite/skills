# Buildkite Build Investigation

Structured workflows for diagnosing failed, flaky, stalled, or anomalous Buildkite builds. This skill encodes a five-phase loop — **Orient → Localize → Correlate → Verify → Record** — and the anti-bias rules that keep an investigation on course. The CLI and MCP tools document their own parameters; this skill focuses on the *sequence* of calls and how to *interpret* the results to reach a root cause.

## Quick Start

The most common case: one build URL, one failed job, infra-vs-test unknown.

```bash
# 1. Orient — fetch build context in one shot
scripts/investigate-build.sh https://buildkite.com/my-org/my-app/builds/42

# 2. Localize — read the failing job's summary, then full log if the summary is thin
bk job log <job-id> --pipeline my-org/my-app --build 42 --print-job-summary
bk job log <job-id> --pipeline my-org/my-app --build 42

# 3. Correlate — check neighbouring builds for the same failure
bk build list --pipeline my-org/my-app --state failed

# 4. Verify — for test failures, hand off to buildkite-preflight; for infra,
#    confirm with a second data source (agent events, kubectl events, Datadog).

# 5. Record — annotate the build with the root cause
buildkite-agent annotate --style "error" --context "root-cause" \
  "OOMKilled in step \`build-image\`; agent queue \`docker-large\` ran out of memory at 2026-05-19T14:02Z"
```

For long-running or many-job builds where the UI itself is slow (PS-1600 pattern), skip the build page entirely and operate through `bk` or the MCP server. See `build-investigation/references/log-search-patterns.md`.

## Investigation Workflow

### Phase 1: Orient

**Purpose.** Frame the failure before reading any log. Get build state, exit codes, retry counts, annotations, meta-data, branch, commit, who triggered, and — critically — whether neighbouring builds failed the same way.

**Signals to look at.**

- Build state: `failed`, `canceled`, `running` (stalled), `not_run`, `blocked`.
- Job-level exit codes and `agent_lost_at` timestamps.
- Annotations already on the build — they are the highest-signal diagnostic surface because they were authored by the pipeline owner specifically for failure triage.
- Meta-data set by earlier jobs (build context, deploy target, upstream commit).
- The cohort: are the last 10 builds for this pipeline all red? Just this one? Every fifth one?

**Tools to use.**

```bash
# Single-shot bundle (recommended)
scripts/investigate-build.sh https://buildkite.com/my-org/my-app/builds/42

# Or individually
bk build view 42 --pipeline my-org/my-app
bk build list --pipeline my-org/my-app --state failed
```

The MCP equivalents are `get_build`, `list_builds`, `list_annotations`. For the command and parameter mechanics, see the **buildkite-cli** skill.

**Exit condition.** Either (a) one specific failed job is the focus and the cohort signal is recorded, or (b) the failure is a fleet-wide cohort and Phase 2 will work across multiple builds.

**UI-too-slow override.** On Anthropic-scale builds (hundreds of jobs, PS-1600 pattern), the build page itself becomes the bottleneck. Switch to `bk` or the MCP server immediately; do not try to investigate through the slow page.

### Phase 2: Localize

**Purpose.** Narrow to one job, one step, one agent, one time window. A diffuse "the build failed" must become "step `test-integration` failed at line 4527 of the log on agent `i-0abc…` in queue `default` at 14:02:13Z".

**Signals to look at.**

- The job's exit code and the last 200 lines of the log.
- The job summary (`--print-job-summary`) — Test Engine summary if present.
- Annotations attached to that job (some pipelines annotate per-job).
- For stalled or never-finished jobs: agent connection events for the agent that owned the job, and — on agent-stack-k8s — Kubernetes events for the pod (A-1110 Dropbox pattern).

**Tools to use.**

```bash
bk job log <job-id> --pipeline my-org/my-app --build 42 --print-job-summary
bk job log <job-id> --pipeline my-org/my-app --build 42
```

For in-UI log search at scale, the standard search box has known regressions (PS-555 cohort, eight customers in 2025). Use API-side substitutes — see `build-investigation/references/log-search-patterns.md`.

For agent-disconnect signatures (`agent lost contact`, exit code -1, `agent_stopped_at` before `finished_at`), see `build-investigation/references/agent-disconnect-diagnostics.md`.

**Exit condition.** A single signature is identified — a stack trace, an exit code, an error string, an "agent lost contact" event, or a missing-events pattern. The signature is what Phase 3 correlates against.

### Phase 3: Correlate

**Purpose.** Link the failure to external state changes. Same error string ≠ same root cause; the same exit code can appear from a dozen unrelated causes. Correlation is what turns a signature into a hypothesis.

**Signals to look at.**

- **Deploys.** Was a new agent image, agent-stack-k8s version, or runtime rolled out near the first failure? PS-1200 (Mistral, pre-command hooks broken after agent 3.106.0 / controller v0.32.0) is the canonical example.
- **Upstream / downstream pipelines.** Triggered builds carry `build_meta_data`; a failure in a child may originate in the parent. PF-9500 (Aiven priority field not cascading) is the canonical "the failure isn't here, it's upstream" case.
- **Webhook event timing.** If a downstream system says the build is still running while the API shows finished, the webhook payload state and the API state disagree. PS-1300 (Spotify, `build.finished` payload reading `"state":"running"`) and PS-505 (Airtable, five-hour ghost build) are the canonical references. See `build-investigation/references/webhook-state-traps.md`.
- **Cohort timing.** All failures since 14:00? Only on `feature/*` branches? Only on the `docker-large` queue?

**Tools to use.**

```bash
# Diff agent versions across the cohort
bk build view 42 --pipeline my-org/my-app   # check BUILDKITE_AGENT_META_DATA
bk build view 41 --pipeline my-org/my-app

# Cross-check webhook payload against canonical state
bk api /organizations/my-org/pipelines/my-app/builds/42
```

> For webhook payload schemas and signature verification, see the **buildkite-api** skill.

**Exit condition.** A specific hypothesis: "this failed because <X>". The hypothesis is testable in Phase 4. If no hypothesis emerges, the cohort is too small — widen Phase 1.

### Phase 4: Verify

**Purpose.** Prove the hypothesis with a second data source. A log line is one observation; a verified root cause requires two independent observations that agree.

**Signals to look at.**

- For test failures: local reproduction with the same env and same commit.
- For infra failures: agent-side logs, Datadog traces, `kubectl get events`, the same job re-run on a different queue, agent connection event history.
- For flake hypotheses: the test's failure rate across the last 50 runs, not a single retry.

**Tools to use.**

- **Local reproduction.** Do not invoke `bk preflight` from inside this skill. Hand the user to the **buildkite-preflight** skill for the local-repro half of verification — that skill owns the snapshot, push, and result-parsing workflow.
- **Kubernetes events.** On agent-stack-k8s, the verification step for empty-log failures is `kubectl get events --field-selector involvedObject.name=<pod>`. PS-1250 (Doordash hugepages — pod spec silently rejected by the scheduler) was diagnosed exactly this way.
- **Datadog / OTel traces.** When the agent and pipeline are instrumented, span data shows the second observation. The agent emits OTel spans for job lifecycle; correlate by `BUILDKITE_BUILD_ID` and `BUILDKITE_JOB_ID`.

> For agent-side failure modes (OOMs, disconnects, pod-spec rejections, agent-version regressions), see the **buildkite-agent-infrastructure** skill — Verify often hands off there.

**Exit condition.** Two independent observations agree, or the hypothesis is rejected and the loop returns to Phase 3 with a new candidate. One retry is not verification; flake suspicions need the statistical view (Test Engine).

### Phase 5: Record

**Purpose.** Leave the investigation visible to the next person — human or agent — who lands on the same build or a sibling failure. An unrecorded investigation is rework next time.

**Signals to leave.**

- A root-cause annotation on the build, using a stable context so a re-run replaces rather than duplicates.
- Meta-data keys that downstream automation can read (the `failure-reason` field Anthropic asked for in PF-9400; encode it as meta-data until the platform ships a first-class field).
- Breadcrumbs for an SRE postmortem: Datadog dashboard link, agent ID, time window, queue name.

**Tools to use.**

```bash
# From inside a job (recommended for automated investigation runs)
buildkite-agent annotate --style "error" --context "root-cause" \
  "Infra: OOMKilled. Step \`build-image\` killed by kernel OOM at 14:02:13Z on agent \`i-0abc…\` in queue \`docker-large\`. See Datadog: <link>."
buildkite-agent meta-data set "failure-reason" "infra-oom"
```

> For annotation styles, context semantics, and meta-data patterns, see the **buildkite-agent-runtime** skill.

Postmortem-grade annotation patterns (root-cause, next-steps, owner, link to incident) live in `build-investigation/references/annotations-for-postmortems.md`.

**Exit condition.** The next investigator landing on this build URL learns the root cause from the build page without re-running any of Phases 1–4.

## Stay on the Path

The investigation loop is short — minutes for a normal build, an hour for a hard one. Skipping phases is the most common cause of wrong diagnoses, and a wrong diagnosis recorded in an annotation poisons the next investigator's prior. Six reasoning patterns appear over and over; each has an override.

**"The cause is obvious — the log says `connection refused`, I'll report that."**
Run Phase 3 (Correlate) anyway. `connection refused` in a build log is the *symptom* of dozens of root causes: agent network policy, sidecar startup race, DNS misconfiguration, service mesh sidecar not ready, target service legitimately down, IAM denial returning a TCP reset. The verification phase is where these separate; do not skip to a fix.

**"I already know this pipeline is flaky."**
Flaky is a hypothesis, not a finding. Run Phase 1 (Orient) to confirm the failure cohort and Phase 4 (Verify) before labelling the failure flaky. PS-555 — the log-search regression — looked like eight independent flakes across eight customers until the cohort was visible from one search.

**"The previous build had the same error, so it's the same cause."**
Same error string is not the same root cause. Confirmation bias is strongest during incidents. Run Phase 2 (Localize) and Phase 3 (Correlate) on the current build; a new deploy, a new agent version, or a new upstream change can produce the same log signature from a different cause.

**"The `build.finished` webhook fired, so the build is definitely finished."**
Not in Buildkite. PS-1300 (Spotify) and PS-505 (Airtable, five-hour ghost build) both document cases where the webhook arrived before the build's terminal state was reconciled. Verify the build state through the REST API (`get_build`) before treating the webhook as authoritative — the API is the source of truth for terminal state. See `build-investigation/references/webhook-state-traps.md`.

**"Retrying the job will tell me if it's flaky."**
One retry is one more data point. A pass on retry could mean the test is flaky, the underlying race resolved itself, the dependent service recovered, or the test was order-dependent and the order changed. Use Test Engine flaky-test analytics for the statistical answer; or annotate the build with the hypothesis and let the cohort accumulate.

**"This is a simple issue, the full workflow is overkill."**
The workflow takes minutes. A wrong diagnosis during an incident costs hours, and a wrong diagnosis recorded in an annotation poisons the next investigator's prior. Follow the loop even on small cases — Phase 5 (Record) alone justifies the cost.

## Failure-Attribution Decision Table

The most common Phase 1 question is *infra or test?* This table maps the eight signatures that account for the majority of red builds to their likely category, the next signal to check, and the downstream skill to hand off to. It encodes the `failure_reason` classification Anthropic asked for in PF-9400; until the platform ships that field as build metadata, compute it here.

| Symptom | Likely category | First signal to check | Skill / reference to use next |
|---|---|---|---|
| Job exit code 137 / `OOMKilled` in log | Infra (memory) | `bk job log` for `Killed` or `OOMKilled`; `kubectl get events` on agent-stack-k8s | **buildkite-agent-infrastructure** (resource class) |
| Job exit code 1 with test-framework output | Test (real failure) | Test Engine summary, `bk job log --print-job-summary` | **buildkite-preflight** for local reproduction |
| Job exit code -1 / "agent lost contact" | Infra (agent disconnect) | Agent connection events; agent-side logs at `agent_stopped_at` | `build-investigation/references/agent-disconnect-diagnostics.md`, **buildkite-agent-infrastructure** |
| Pipeline upload step fails with YAML error | Config | Upload step's log, `buildkite-agent pipeline upload --dry-run` locally | **buildkite-pipelines**, **buildkite-dynamic-pipelines** |
| Stalled, no exit code, log empty | Infra (k8s scheduler / network) | Missing-events signature (A-1110 Dropbox); `kubectl get events --field-selector ...` | `build-investigation/references/agent-disconnect-diagnostics.md`, **buildkite-agent-infrastructure** |
| Build state inconsistent vs webhook payload | Upstream (event timing) | Compare `get_build` REST response vs webhook payload | `build-investigation/references/webhook-state-traps.md`, **buildkite-api** |
| Same job fails when triggered, passes on direct run | Upstream (parent meta-data) | `build_meta_data` from triggering build | **buildkite-pipelines** (trigger step), **buildkite-agent-runtime** (meta-data) |
| New failure starting after a tool / agent upgrade | Regression (agent or stack) | Diff agent versions and stack versions across the cohort | **buildkite-agent-infrastructure** |

## Common Mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Reading only the failing job's log and stopping | Misses the cohort signal — a flake or a fleet-wide regression looks like a single failure | Run Phase 1 (Orient) — `bk build list --state failed` to see the cohort before reading any log |
| Treating the `build.finished` webhook payload as authoritative for state | Downstream system thinks the build finished when it is still reconciling (PS-1300, PS-505) | Verify via REST `get_build` before acting on the webhook |
| Conflating exit code 137 with "test failed" | Wrong fix (rewrite the test) when the real cause is memory pressure | Use the Failure-Attribution Decision Table — 137 is OOM, not a test signal |
| Retrying a flaky-looking job and declaring it fixed when it passes | Hides the intermittent failure and repeats next run | Annotate the build with the flake hypothesis; capture the failure for Test Engine to count |
| Investigating in the UI on a many-job build (PS-1600 pattern) | The build page is itself slow; investigation budget is spent waiting on renders | Switch to `bk` CLI or MCP `get_build` for builds with more than a few dozen jobs |
| Skipping Phase 5 (annotation) on "obvious" failures | The next investigator redoes the work; the root cause never propagates | Always annotate with `--context root-cause` — even one line beats no record |
| Asking "is this flake?" without checking neighbouring builds | Every fifth failure looks flaky in isolation | Pull the last twenty builds for the pipeline before answering |
| Reproducing locally against the current working tree | Misses the env-var or secret that caused the failure in CI | Capture the failing build's env via `buildkite-agent env dump` (or an annotation), then reproduce with **buildkite-preflight** |

## Anti-Scope

This skill stops at *you know what to change*. The fix itself belongs elsewhere.

- **Running CI against local uncommitted changes** — **buildkite-preflight**. This skill assumes the failed build already exists.
- **Agent infrastructure operations** (sizing, cluster setup, queue capacity, agent-stack-k8s configuration) — **buildkite-agent-infrastructure**. This skill identifies infra causes and hands off.
- **Hosted-agent operations** (image lifecycle, macOS specifics, namespace concurrency) — **buildkite-hosted-agents-operations**.
- **Webhook payload reference** (full event schemas, signature verification, replay defence) — **buildkite-api**.
- **Pipeline YAML authoring and step types** — **buildkite-pipelines**.
- **`bk job log` flag reference and CLI installation** — **buildkite-cli**.
- **Writing tests, test splitting, Test Engine flaky detection** — planned **buildkite-test-engine** skill.
