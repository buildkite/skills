# Buildkite Hosted Agents Operations

This skill covers operating Buildkite-managed hosted agents — pushing custom Linux images to the internal container registry, choosing Xcode versions on macOS, sizing cache volumes, debugging namespace concurrency errors, and using terminal access. It is the runbook for once hosted is the chosen architecture; for that choice itself, see the **buildkite-agent-infrastructure** skill.

## Quick Start

Identify the symptom and route to the matching section. Hosted is a black box on purpose: do not try to recover host filesystem state across jobs (it is destroyed), do not install software in a job that should live in a custom image, and do not exec into a finished job — the VM is gone.

| Image won't update / Dockerfile-in-UI is awkward | Image Lifecycle (Linux) |
| Mac/iOS build failing on hosted                  | macOS Hosted Agents |
| Xcode N broke our build                          | macOS Hosted Agents |
| Cache volume hit/miss confusion                  | Cache Volumes |
| "Spike in errors in namespace"                   | Namespace Integration and Concurrency |
| Concurrency cap hit / jobs queue silently        | Namespace Integration and Concurrency |

| Pipeline runs locally but not on hosted          | Terminal Access |
| "Should we even use hosted?"                     | **buildkite-agent-infrastructure** |

The minimum-viable shape for a hosted pipeline is the same as any other Buildkite pipeline; just target a hosted queue:

```yaml
# .buildkite/pipeline.yml
agents:
  queue: "hosted-linux"     # the hosted-Linux queue created in the Buildkite UI

steps:
  - label: ":hammer: Test"
    command: "npm ci && npm test"
    cache:
      paths:
        - "node_modules"
      size: "20g"
```

`cache:` works on hosted only when the cluster has cache volumes enabled — see Cache Volumes below.

## Hosted vs Self-Hosted — Operating-Day Differences

The full decision tree lives in **buildkite-agent-infrastructure** Phase 1. The five operating-day differences:

| Capability | Hosted gives you | Self-hosted gives you |
|---|---|---|
| Image control | Default base image, UI Dockerfile editor, or custom image URL via internal container registry. Linux only. | Anything you can build into an AMI, Kubernetes pod spec, or container image. |
| OS support | Linux (AMD64/ARM64) and macOS (Apple silicon M4 only). | Linux, macOS (your hardware), Windows, BSD, anything an agent binary runs on. |
| Network egress | Shared NAT IP ranges, not strictly static. Use OIDC for outbound auth. | Your VPC, your egress, your allowlists. |
| Concurrency model | Plan-gated: max combined vCPU / instance-shape vCPU. | Your fleet size, your scheduler, your cost. |
| Debug access | Browser terminal during a running job. VM destroyed at end. | SSH to the host, snapshot it, retain state, run a debugger. |

Hosted exists so a five-engineer mobile team can ship without a platform team. With a platform team and a VPC mandate, hosted is the wrong choice.

## Image Lifecycle (Linux hosted agents)

Linear A-500 (Groq) anchored this section: *"the only way to update images is copy-paste Dockerfile in UI, breaking auth-bootstrap flows."* That is the workflow gap this section addresses.

Three image-management modes:

**1. Default Buildkite image.** Ubuntu 22.04 with `docker`, `docker-compose`, `docker-buildx`, `git-lfs`, `node`, `aws-cli`. Use during proof-of-concept or when there is genuinely no extra tooling required. Anti-rule: do not install tools at job start to avoid creating a custom image — that cost compounds across every job, every run.

**2. Custom agent image via the Buildkite UI Dockerfile editor.** The `FROM` line is fixed and managed by Buildkite; `USER` cannot be changed; `UID` and `GID` environment variables are unsupported. Once an image is created it cannot be edited — only deleted (after no queue references it) and recreated. Treat the UI editor as an immutable image factory, not a working surface. Suitable when the image is small, rarely changes, and is built by one person.

**3. Custom image URL via the internal container registry.** Build the image in a pipeline step, push to `$BUILDKITE_HOSTED_REGISTRY_URL/your-image:tag`, and set the queue's **Image URL** field on the **Base image** tab. The pattern A-500 was asking for. Build-in-pipeline mirrors the docs example:

```yaml
agents:
  queue: "linux-small"

steps:
  - key: create_custom_base_image
    label: ":docker: Create custom base image"
    if_changed:
      - ".buildkite/Dockerfile.build"
      - ".buildkite/pipeline.yml"
    command: |
      docker buildx build \
        --file .buildkite/Dockerfile.build \
        --platform linux/amd64 \
        --tag "${BUILDKITE_HOSTED_REGISTRY_URL}/base:latest" \
        --push .
```

> The custom **Image URL** feature is in **private preview**. Contact `support@buildkite.com` to enable for your organization. The internal container registry itself is Enterprise-only. Flag both constraints before recommending this mode.

A CLI helper for the build-and-push half of this workflow is bundled at `scripts/hosted-image-build-and-push.sh`.

**Required tools in any custom image** (per `linux/custom_agent_images.md`): `git`, `ca-certificates`, `bash`. The `ca-certificates` omission is the single most common silent break — without it the agent cannot complete TLS handshake with the Buildkite platform and the job never starts.

**Embedding hooks in a custom image.** Set `BUILDKITE_ADDITIONAL_HOOKS_PATHS` to a directory you control and `COPY` hook scripts into that directory. Do not point `BUILDKITE_ADDITIONAL_HOOKS_PATHS` at `/buildkite/agent/hooks` — that path is fixed, read-only, and overwritten at job start.

```dockerfile
ENV BUILDKITE_ADDITIONAL_HOOKS_PATHS=/custom/hooks
COPY ./hooks/*.sh /custom/hooks/
```

`pre-bootstrap` and agent-lifecycle hooks are not supported on hosted; only the job-lifecycle hooks (`environment`, `pre-checkout`, `checkout`, `post-checkout`, `pre-command`, `command`, `post-command`, `pre-artifact`, `post-artifact`, `pre-exit`) run.

> For what hooks actually do at runtime, see the **buildkite-agent-runtime** skill. This section covers only baking them into a hosted image.

For full worked examples of all three modes, hook-directory layouts, and the "Issues with starting a job" decoder, see `hosted-agents-operations/references/image-lifecycle-patterns.md`.

## macOS Hosted Agents — Xcode, Code-Signing, the Read-Only Filesystem Trap

> 7 customers escalated Mac/iOS or hosted-image pain in the last 12 months: Tinder, SafetyCulture, Doordash, Twilio, Ramp, Airtable, Improbable. Mac/iOS is the single largest hosted-agent escalation cluster.

Three operating rules:

**1. No custom macOS base image.** Apple silicon only. The biggest divergence from Linux hosted. Software installs in-job via Homebrew; persistence is via cache volumes; there is no "base image" to maintain. Per the docs: *"While you currently cannot provide custom base images for macOS hosted agents... you do have significant control over these virtual machines during job execution."*

**2. Xcode tracks Apple by one week.** Per the docs: *"Updated Xcode versions will be available one week after Apple offers them for download. This includes Beta, Release Candidate (RC), and official release versions."* Pin Xcode explicitly in the Fastfile or `xcodebuild` invocation — never assume "latest available". As of 2026-05-20, macOS Tahoe carries Xcode 26.0–26.3 and 16.4; Sequoia carries Xcode 15.4–26.4-beta2; Sonoma is on Xcode 14.3.1–16.3. Decision rule: for Xcode ≥26, choose Tahoe or Sequoia; Sonoma is end-of-life for new Xcode. The canonical table lives in `macos.md` and rotates; do not memorise it.

**3. Reserved-path filesystem trap.** On macOS hosted, `/tmp` and `/private` are reserved and cannot be used as cache mount points (Linear PS-1000, Equilibrium Energy). Mount sub-paths instead — `/tmp/volume` is acceptable, `/tmp` is not.

**Code-signing decision table** (from `macos/troubleshooting_fastlane.md`):

| Symptom | Likely cause | First fix |
|---|---|---|
| `The sandbox is not in sync with the Podfile.lock` | `pod install` is not running in CI | Add `cocoapods()` or `cocoapods(clean_install: true)` to the fastlane lane |
| `bundler: failed to load command: fastlane` with `mutex_m` / `ostruct` / `abbrev` warnings | Ruby 3.4+ removed those stdlib gems; hosted Macs ship Ruby 3.4+ via Homebrew | Add `gem 'mutex_m'`, `gem 'ostruct'`, `gem 'abbrev'` to the `Gemfile` |
| `CodeSign ... Exit status: 65` | Certificate, profile, keychain, or team-ID mismatch | Switch to `fastlane match`; verify identity with `security find-identity -v -p codesigning` via terminal access |

Hard-line: use `fastlane match` rather than hand-rolling certificate and profile management. The hosted Mac is ephemeral — every job starts with no identities loaded. `match` makes that fast; hand-rolling makes it a nightmare.

The Xcode/iOS/Ruby gotcha table at full depth, plus a `match` setup walkthrough, lives in `hosted-agents-operations/references/macos-build-gotchas.md`.

## Cache Volumes — When to Enable and How Big

Cache volumes are off by default; opt in per pipeline via the `cache:` key in YAML, or globally via the cluster's **Cache Storage** settings. **Retention is 14 days from last use, on a best-effort basis** — volumes can evict earlier. Volumes are non-deterministic: a `docker pull` against a container cache volume may hit the cache or may fall through to the origin registry. Design steps to handle a miss.

| Workload | Use what | Size |
|---|---|---|
| `node_modules`, `vendor/bundle`, build outputs | Step-level `cache:` paths | 20 GB default; up to ~50 GB typical |
| Docker layer cache between builds | Container cache volumes (cluster-level toggle, Linux only) | Auto-grown |
| Large monorepo git clone | Git mirror volumes (cluster-level toggle) | Auto-grown per repo |
| OCI images required every job, deterministically | **Internal container registry**, not a cache volume | N/A |

The critical rule, verbatim from `internal_container_registry.md`: *"If you need deterministic storage for OCI images... you can use your internal container registry instead of a cache volume."* Cache volumes are best-effort; the internal container registry is durable storage.

**Concurrency knob.** `BUILDKITE_CACHE_CONCURRENCY` controls how many cache volumes are saved/restored in parallel. Default `2`; raise for pipelines with many small volumes; set `0` or negative to match the available CPU count.

For sizing math, the Node/Ruby/Go/iOS-DerivedData worked examples, and the macOS sparse-bundle caveat, see `hosted-agents-operations/references/cache-volume-sizing.md`.

## Namespace Integration and Concurrency — Reading the Opaque Admin UI

Linear PS-400 (11x.ai) anchored this section: *"Builds are failing, Seeing a Spike in Errors in Namespace — namespace.so errors visible only via separate admin UI."*

Three operational rules:

**1. Concurrency is plan-gated and divides by instance shape.** Linux hosted concurrency = `max combined vCPU / instance-shape vCPU`. With 48 max combined vCPU and `LINUX_AMD64_4X16` (4 vCPU per agent), that is 48 / 4 = 12 concurrent agents. macOS uses the same arithmetic against the plan's Mac M4 concurrency. Anti-pattern: do not budget concurrent agents from the plan page alone — budget against the largest instance shape in use. Provisioning Large (8 vCPU) halves concurrency relative to Medium.

**2. When concurrency is exhausted, jobs queue silently.** No error in pipeline logs. The signal is wait time. Alert on P95 hosted-queue wait time > 60s as a proxy for concurrency exhaustion.

**3. namespace.so errors surface in a separate admin UI, not on the build page.** This is the 11x.ai pain (PS-400) and it is a product gap, not a user error. **Action when a customer reports "spike in errors in namespace":** gather the timestamp, point at the cluster's hosted-agent operational view, and escalate to `support@buildkite.com`. Do not invent a fix — the customer cannot self-serve this today. Flag the limitation honestly.

Concurrency arithmetic worked examples per plan tier, the alert-on-wait-time runbook, and the (limited) namespace.so error decoder live in `hosted-agents-operations/references/namespace-and-concurrency.md`.

## Network Security — IP Allowlists and OIDC

Hosted agent IP ranges are visible per queue under **Networking → Network Ranges**. They are **not strictly static** — Buildkite warns ahead of changes, but allowlists built against the ranges will need updating. Per `network_security.md`: *"secure communications with OIDC ... OIDC tokens issued by Buildkite hosted agents ... can be used to verify that network communications originate from those agents."*

Hard-line: if OIDC is an option for outbound auth, use OIDC. IP allowlists are for VPN-constrained customers; they are brittle and break every time the range shifts.

> For OIDC subject claims, federation patterns, and `buildkite-agent oidc request-token`, see the **buildkite-secure-delivery** skill and the **buildkite-agent-runtime** skill.

**Code access.** GitHub private repositories work natively via OAuth with a 50-minute access-token cache. Non-GitHub providers require the `git-ssh-checkout` plugin plus an SSH private key stored as a cluster secret. Pipeline-migration paper-cut from `pipeline_migration.md`: existing repos **must be switched to HTTPS checkout** in pipeline settings before they can run on hosted agents.

## Terminal Access — When to Open, What to Look For

Terminal access is the hosted-agent equivalent of `kubectl exec` and the highest-leverage debugging tool available. Available to users with build permissions on the pipeline, cluster maintainers, and organization administrators. Organization admins can disable it cluster-wide; confirm it is active before assuming a customer can use it.

Open a terminal when:
- A build fails on hosted but passes locally.
- A custom image misbehaves and tooling needs inspection.
- A hook needs to be tested before baking into an image.

Do not open a terminal as a workaround for missing tooling — fix the image instead.

Extend the session with a `sleep` in the step command so the VM does not tear down mid-investigation:

```yaml
steps:
  - label: "Extend Terminal Session"
    command: |
      echo "Starting job..."
      sleep 600
      echo "Job complete."
```

The terminal opens via the **Open Terminal** button on the running job's step in the Buildkite UI.

## Cost, Billing, and Plan Gating

Per-second billing applies to command execution time only (not startup or teardown). Cache volumes and Git mirroring carry no additional cost. Plan gating to confirm before recommending a feature:

## Common Mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Editing the Dockerfile in the UI and expecting to iterate | Images are immutable; only deletion + recreate (A-500) | Build in a pipeline step, push to `$BUILDKITE_HOSTED_REGISTRY_URL`, set the queue's **Image URL** |
| Custom image missing `ca-certificates` | TLS handshake fails; jobs never start | Always include `git`, `ca-certificates`, and `bash` |
| Assuming Xcode "latest" is stable on Apple release day | Build breaks the week Apple ships | Pin Xcode explicitly; hosted lags Apple by one week |
| Treating cache volumes as durable storage | Volumes evict at 14 days, best-effort | Design for cache miss; for deterministic OCI use the internal container registry |
| Hand-rolling iOS code signing | Exit 65, mysterious provisioning failures | Use `fastlane match`; verify with `security find-identity -v -p codesigning` |
| Setting `cache:` on macOS reserved paths (`/tmp`, `/private`) | Mount silently rejected (PS-1000) | Mount sub-paths only — `/tmp/volume`, not `/tmp` |
| Budgeting concurrency against plan vCPU without dividing by instance shape | Half the agents expected | Concurrency = plan vCPU / instance-shape vCPU; budget against the largest shape |
| Ignoring namespace.so errors in the separate admin UI | Failures look pipeline-side but are infra-side (PS-400) | Check the operational view; escalate to support if persistent |
| Allowlisting hosted agent IPs as static | Allowlist breaks silently on a range change | Use OIDC where possible; otherwise subscribe to range-change notifications |
| Job-time `apt install` instead of a custom image | Every job pays the install cost; flaky network surfaces as flaky build | Bake tooling into a custom Linux image; on macOS, cache Homebrew |
| Trying to open terminal on a finished job | The VM is gone (ephemeral by design) | Open during the running job; extend with `sleep N` |
